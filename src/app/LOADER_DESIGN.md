# 电子负载软件设计思路

> 目标：单通道、实验板级（&lt;50W 量级）、CC/CV/CR/CP 全模式。  
> 人机：TFT + MujicaUI + 按键；调试：串口 CLI/日志。  
> 现状：功率级硬件未定 → **先定接口与分层，用 mock 跑通控制与状态机**。

本文只讲**怎么拆、怎么写、依赖怎么走**，不展开具体寄存器与引脚。

---

## 1. 总体分层（工程级）

沿用本仓库已有结构，电子负载**不要**全部堆在 `app` 里。

```
┌─────────────────────────────────────────────────────────┐
│  app/loader          产品：状态机、模式、任务、UI/CLI     │
├─────────────────────────────────────────────────────────┤
│  service             领域能力：采样物理量、保护、标定     │
├─────────────────────────────────────────────────────────┤
│  driver / bsp        硬件边界：ADC/DAC/使能/风扇…         │
├─────────────────────────────────────────────────────────┤
│  common              纯算法：PID、滤波、限幅、工具         │
└─────────────────────────────────────────────────────────┘
         依赖只能向下，禁止 service/bsp 反包含 app
```

| 层 | 一句话职责 | 电子负载里放什么 |
|----|------------|------------------|
| **common** | 换板子还能用 | `pid`、`filter`、数值限幅 |
| **bsp/driver** | 只认硬件 | 读 raw ADC、写 DAC/PWM、负载使能 GPIO |
| **service** | 认物理量与规则 | V/I 标定滤波、OVP/OCP 判定、校准表 |
| **app** | 认「这台负载」 | 模式、状态机、控制编排、UI、CLI |

判断标准：

- 代码里出现 **「设定电流 / CC 模式 / 故障恢复」** → 多半是 **app**
- 代码里出现 **「毫伏、安、滤波后测量值」** → **service**
- 代码里出现 **「ADC 码值、DAC 码值」** → **bsp**
- 代码里只有 **「误差、积分、Kp」** → **common**

## 2. app 内部怎么分层

建议把 `src/app` 下电子负载相关收拢为逻辑上的几块（文件可先平铺，模块边界要清）：

```
app（loader 产品层）
│
├── runtime     共享运行时状态（唯一「真相源」）
├── fsm         工作状态机（Idle / Run / Fault / …）
├── mode        模式与设定点（CC/CV/CR/CP → 控制目标）
├── control     控制环（读测量 → PID → 写输出请求）
├── ui          菜单/显示/按键（只改设定，不写 DAC）
├── cli         串口命令/日志（同 UI：只动设定与查询）
└── task        FreeRTOS 任务与周期调度（胶水）
```

### 2.1 runtime：共享状态，不要到处传散装变量

所有模块围绕一份 **runtime**，避免 UI 一套变量、控制又一套。

思路上包含三类数据：

1. **设定（人写）**  
   模式、设定值、输出开/关、限值（可与 config 默认合并）
2. **测量（环写）**  
   电压、电流、功率、温度（来自 service）
3. **运行结果（环写）**  
   控制输出、故障码、当前状态

约定：

- **写执行器**：只允许 control 路径（经 fsm 允许后）
- **写设定**：UI / CLI / 将来的上位机
- **读测量**：谁都可以读；写测量只有 sense 更新路径

### 2.2 fsm：管「能不能输出」，不管「PID 怎么算」

状态建议从简：

```
        上电/初始化
             │
             ▼
          IDLE ──────── 按键/命令 ON 且无故障 ──────► RUN
             ▲                                          │
             │                     保护触发 / 命令 OFF    │
             │◄─────────────────────────────────────────┤
             │                                          │
             └──── 清除故障 / 确认  ◄──── FAULT ◄────────┘
```

| 状态 | 含义 | control 是否允许驱动功率级 |
|------|------|----------------------------|
| IDLE | 待机，可改设定 | 否（输出强制 0 / 关闭使能） |
| RUN  | 加载中 | 是 |
| FAULT| 保护锁定 | 否，需明确恢复步骤 |

fsm 只决策：**开/关输出、进故障、是否接受模式切换**。  
不要在 fsm 里写 PID。

### 2.3 mode：把四模式收成「控制目标」

不要一上来做四套完全独立的控制环。推荐：

> **内环统一做电流（或统一做一种物理量）**；  
> CV/CR/CP 只负责算出「本周期目标电流 / 目标电压」。

| 模式 | mode 层做什么 | control 层做什么 |
|------|---------------|------------------|
| **CC** | `I_target = I_set` | 电流闭环跟 `I_target` |
| **CV** | 根据 V 误差生成 `I_target`（或限流下的电压环） | 跟 `I_target`，并限幅 |
| **CR** | `I_target = V_meas / R_set` | 同上 |
| **CP** | `I_target = P_set / max(V_meas, ε)` | 同上 |

这样 control 始终是：**目标 vs 反馈 → PID → 执行量**，模式切换主要换「目标怎么来」。

### 2.4 control：纯周期控制，无 UI、无 printf

每个控制周期固定三步：

1. 取最新测量（service）
2. 问 mode 要本周期目标
3. PID 计算 → 限幅 →（若 fsm 允许）请求输出

细节见第 3 节。

### 2.5 ui / cli：人机只碰设定

- 显示：读 runtime（V/I/P、模式、状态、故障）
- 输入：改 mode、setpoint、output_on
- **禁止**：UI 任务里直接 `HAL_DAC` / 写 GPIO 使能

串口 CLI 与 UI 同级：同一套设定接口，避免两套逻辑。

### 2.6 task：胶水与节奏

| 谁 | 周期量级 | 职责 |
|----|----------|------|
| 控制任务（高优先级） | 1–10 ms | sense → protect → mode → control → 输出 |
| UI 任务（低） | 20–50 ms | 按键、菜单、刷屏 |
| CLI/日志 | 事件/空闲 | 解析命令、打 log |

硬件未定时，控制任务里 sense/输出可以是 mock，但**任务切分和周期先定死**。

### 2.7 app 模块依赖（只允许实线方向）

```
   ui ──┐
   cli ─┼──► runtime ◄── control ◄── mode
        │       ▲            ▲
        │       │            │
        └──►  fsm ───────────┘
                │
   task 调用：fsm / control / ui；不承载业务公式
                │
                ▼
            service（sense / protect）
                │
                ▼
              bsp
```

## 3. 控制部分怎么写（核心思路）

### 3.1 控制环的位置

- **算法积木**（PID 本体）→ `common/pid`（已有就复用）
- **环的编排**（何时算、目标从哪来、输出到哪去）→ `app` 的 control
- **测量从哪来** → service，control 不解析 ADC raw
- **DAC 怎么写** → bsp，control 只给出「0~满量程」或物理量请求，由一层转换

推荐边界：

```
control 输出：float out_norm  ∈ [0, 1]  或  目标栅压/占空比抽象值
     ↓
bsp/load_out：映射到 DAC code / PWM，并处理使能时序
```

这样换 DAC 芯片时 control 不用改。

### 3.2 单周期伪代码（心智模型）

```text
// 仅在 RUN 且无新故障时真正输出
meas = sense_get()
fault = protect_check(meas, limits)
if fault:
    fsm → FAULT
    output_disable()
    return

target = mode_compute_target(mode, setpoint, meas)   // 如 I_target
u = pid_step(pid, target, meas.i)                    // 例：电流内环
u = clamp(u, 0, u_max)

if fsm_state == RUN && output_on:
    load_out_set(u)
else:
    load_out_set(0) / disable
```

### 3.3 四模式在 control 里的落地顺序

不要并行开四套 PID。建议实现顺序：

1. **CC + 保护 + 开关机**（验证整条实时链路）
2. **CR / CP**（纯代数算 `I_target`，仍走同一电流环）
3. **CV**（电压外环生成 `I_target`，或带限流的电压环；注意稳定性）

CV 比 CR/CP 更难：有源带载时电压环容易抖，优先限流、限斜率。

### 3.4 与保护的关系

- **protect**：只做判定（是否超限、哪一类故障）
- **fsm**：决定关断与锁定
- **control**：看到非 RUN 或故障 → 输出清零

保护逻辑不要散落在 UI 和 CLI 里各写一遍。

### 3.5 标定与滤波放哪

| 内容 | 层 |
|------|-----|
| 滑动平均 / 低通 | common 或 service 内调用 common |
| raw → 伏特/安培 | service（带校准系数） |
| 控制用哪路滤波后的量 | service 提供「控制用」与「显示用」若需要可分开带宽 |

显示可以更稳（滤波更重），控制可以略快（滤波更轻）——若需要，在 sense 里出两路，而不是在 control 里再滤一套说不清的数。

### 3.6 Mock 阶段 control 怎么写

硬件未定也要把 control **按真环写**：

- `sense_get()`：返回可调的假 V/I（或随「假 DAC」变化的简单模型）
- `load_out_set(u)`：只记录 u，并可选地反推假电流 `I = f(u)`
- 这样可调 PID、测模式切换、测故障注入，板子来了只换 bsp/service 底层

## 4. 和仓库现有文件的对应关系

| 现有 | 建议角色 |
|------|----------|
| `loader_task.h` / 任务相关 | task + runtime 类型定义 |
| `loader_control.c` | control 环编排 + 持有 pid 实例 |
| `loader_ui.c` | ui，只绑设定与显示 |
| `loader_config.h` | 默认限值、默认 PID、周期、满量程 |

可逐步拆出（不必一次拆完）：

- `loader_fsm.*` — 状态
- `loader_mode.*` — 四模式目标计算
- `loader_runtime` 结构 — 可放在 `loader_task.h` 或独立头文件

## 5. 设计原则（写代码时用来拍板）

1. **一个真相源**：设定与测量以 runtime 为准。  
2. **一个写执行器的人**：control（且受 fsm 门控）。  
3. **一个故障决策点**：fsm + protect，禁止多处关断策略不一致。  
4. **模式换目标，不换整套架构**：优先统一内环。  
5. **先接口后硬件**：bsp 可 mock，app/service 形状尽量稳定。  
6. **实时与人机分离**：控制任务短而固定；UI/日志可慢、可堵。

---

## 6. 建议的落地节奏（思路级）

```
① 定 runtime + fsm(IDLE/RUN/FAULT)
② mock sense / load_out
③ CC 控制环 + 输出开关
④ 简单 OCP/OVP → 进 FAULT
⑤ UI 显示与改设定
⑥ CLI 查询/设定
⑦ CR、CP（算 I_target）
⑧ CV
⑨ 真硬件替换 mock + 标定
```

---

## 7. 一句话总结

- **工程分层**：硬件进 bsp，物理量与保护进 service，算法进 common，产品逻辑进 app。  
- **app 分层**：runtime 作中心；fsm 管许用；mode 管目标；control 管闭环；ui/cli 只改设定；task 管节奏。  
- **控制写法**：统一内环 + 模式算目标；周期内固定「测→护→算→写」；硬件用 mock 先把环跑稳。

后续若硬件原理图确定，只需补：采样通道、执行器类型、限值数字表，以及 `doc/hardware.md`——**不必推翻上述分层**。
